# Решения по Yakov Viewer

Этот файл фиксирует текущие решения из обсуждения, простым языком.

## Как работаем

Пользователь часто надиктовывает сообщения голосом в шумной обстановке. Распознавание может путать слова, названия доменов, файлы и технические термины.

Практическое правило: перед опасными или внешне видимыми действиями нужен короткий бриф на 2-4 строки. Если фраза выглядит странно или противоречит уже принятому направлению, нужно уточнить, а не исполнять дословно.

На текущем этапе проект ведем в одном основном чате/потоке, без постоянного второго агента. Второй чат для backend/Cloudflare имеет смысл открывать после первого настоящего upload milestone: JPEG загружается в R2, metadata пишется в D1, фото видно в админке из Cloudflare-backed данных.

Подробные рабочие рельсы: `docs/working-rails.md`.

## Главная идея

Yakov Viewer - это публичный сайт-портфолио фотографа Якова Шмоля и одновременно основа для большой общей фотоархивной системы.

Визуальным контрактом публичного сайта с 17 июля 2026 года является готовый frontend из локальной папки:

```txt
/Users/jacobshmol/Documents/q5/proj/yakov/
```

В нем находятся 9 реальных альбомов и 312 реальных фотографий. При интеграции переносим дизайн, поведение и контентную структуру, но не копируем JPEG, thumbnails или `dist` в Git. Медиа должны попасть в R2 отдельным импортом.

Figma для первой рабочей версии не требуется. Сначала переносим существующий интерфейс максимально близко к оригиналу, затем улучшаем его небольшими проверяемыми итерациями.

Админка - это важная самостоятельная часть проекта. Она нужна не только для управления публичным сайтом, но и как private-хранилище: там могут лежать сеты, альбомы и фотографии, которые никогда не будут опубликованы.

Эта же база и это же хранилище должны в будущем использоваться и для Logjamming, чтобы не загружать один и тот же архив дважды.

## Структура архива

Базовая структура:

```txt
Сет
  Альбом
    AlbumPhoto membership
      Фотография
        Версии файла

Коллекция
  Выбранные фотографии из разных альбомов

Все фотографии
  Опубликованные фото с фильтрами по тегам
```

Главная сущность - альбом. Альбом работает как папка или пленка: например, `Film 060` с 36 фотографиями или цифровая серия с 30 фотографиями.

Фотография является самостоятельной сущностью и может входить в несколько альбомов без копирования файла. Порядок фотографии хранится в связи `AlbumPhoto`, а `Asset` принадлежит одной канонической фотографии.

Один альбом может относиться к нескольким сетам. Сет - это большая публичная/редакторская секция из альбомов: например, `Bangkok`, `Mountains`, `Milky Way Timelapse`.

Теги должны быть из единого справочника, чтобы не плодить варианты вроде `Bangkok`, `bangkok`, `BKK`.

Отдельно будут коллекции: выбранные фотографии из разных альбомов. Например, `Selected Work`, `Portfolio 2026`, `Best of Film`. Коллекция не копирует файлы, а ссылается на уже загруженные фото.

У альбомов и фотографий будут теги. Фотография автоматически наследует теги своего альбома, а дополнительно ей можно назначить собственные теги. У сетов тегов пока не будет: сет сам является большим объединением альбомов.

Практическое правило:

- сет содержит альбомы;
- альбом содержит фотографии;
- коллекция содержит отдельные фотографии;
- фото-тег описывает конкретный кадр;
- режим "все фотографии" позволяет фильтровать кадры по тегам и унаследованным тегам альбома.

## Файлы фотографий

Текущая загрузка создает три web-уровня:

```txt
thumb        - маленькое превью, примерно до 300 KB
display      - версия для просмотра на сайте, примерно около 1 MB
expanded     - очищенный загруженный JPEG, обычно 3-5 MB, максимум 20 MiB
```

Все три версии хранятся в public R2. Обычные сетки используют `thumb`, нормальный
просмотр - `display`, а кнопка `+` лениво подгружает `expanded`.

Кнопка Download включается на уровне альбома. Она отдает тот же `expanded`, не создавая
четвертую копию. При выключенном Download увеличение продолжает работать.

Полные 20-50 MB оригиналы, RAW/RAF/TIFF и панорамы пока остаются в Google Drive.
`sourceJpeg`, `downloadJpeg` и `master` сохранены в модели как будущие типы, но текущий
upload их не создает.

## Публикация

Желаемый flow:

```txt
загрузил фото
  -> система создала web-версии
  -> фото попали в draft/review
  -> владелец проверил порядок, теги, обложки, видимость
  -> владелец нажал publish
```

Публикация должна быть осознанным действием. Не надо автоматически выкладывать все сразу после upload.

Первый upload принимает только JPEG до 20 MiB. Типичный входной файл уже подготовлен
для сайта: около 2000 px и 3-5 MB. Браузер создает `thumb` и `display`, а очищенный от
EXIF/XMP/IPTC входной JPEG становится `expanded`. Внешний Google Drive архив остается
источником полных оригиналов.

RAW/RAF/TIFF можно сразу держать в модели как будущий `master`-файл, но в первой реальной загрузке не надо на этом застревать. Эти файлы позже будут приватными архивными исходниками или доступом для выбранных пользователей.

## Hidden, Bin, Delete

`hidden`:

- фото пропадает с публичного сайта;
- фото пропадает из публичных коллекций и режима "все фотографии";
- фото остается в админке;
- файлы остаются в R2;
- фото можно вернуть обратно.

`trash` - внутренний статус записей в разделе `Bin`:

- фото временно в корзине;
- можно восстановить;
- можно настроить автоудаление, например через 7 дней.
- если альбом уходит в корзину, его фотографии тоже уходят в корзину и исчезают отовсюду публично.

`delete`:

- фото и связанные файлы полностью удаляются из Cloudflare R2;
- действие необратимо после окончательного удаления.

## Обложки

По умолчанию первая фотография назначается сразу во все три слота обложки.

Текущая рабочая модель:

- landscape, square и portrait - три независимых назначения;
- каждое назначение выбирается из фотографий альбома в инспекторе кадра;
- `Preferred shape` отдельно задает приоритет формата для поддерживающих его layouts
  и не меняет сами назначения;
- отдельная загрузка cover-only файла и crop editor остаются последующим этапом.

## Цвет

Для первых web-версий лучше использовать предсказуемый web-pipeline:

- `thumb` и `display` делать в sRGB;
- у `expanded` сохранять ICC profile и JPEG scan bytes, когда ориентация не требует
  полного re-encode;
- GPS и чувствительный EXIF не публиковать.

Позже можно добавить расширенную настройку: сохранять P3/широкий цветовой профиль для web-версий там, где это действительно нужно.

## Cloudflare

Целевая инфраструктура:

```txt
Next.js + OpenNext Worker - публичный сайт, /admin и API
Cloudflare Access         - вход в админку для владельца
Cloudflare R2             - файлы фотографий
Cloudflare D1             - сеты, альбомы, membership, фото, статусы, теги
Cloudflare Queues          - обработка изображений, когда понадобится
```

Старый статический Pages deployment не является архитектурным контрактом. Для новых динамических альбомов используем один full-stack Worker, чтобы публикация из админки не требовала пересборки сайта.

Пока первые реальные загрузки стабилизируются, production deploy выполняется вручную
через Wrangler после полного check. GitHub automatic builds подключаем отдельным
этапом, когда этот release rail станет предсказуемым.

Рабочее правило для инфраструктуры: Cloudflare настраиваем и обновляем через Wrangler
или Cloudflare API. Браузер не используем как основной способ автоматизации. Перед
любым удаленным созданием ресурса, миграцией, upload, deploy или переключением домена
Codex сначала дает короткий бриф с точными именами и средой, затем получает
подтверждение.

Полный локальный backend-срез уже проверен: JPEG проходит через защищенный Worker, три
web-версии пишутся в public R2, а `Photo`, `AlbumPhoto`, `Asset` и `UploadJob` -
в D1. Все основные mutation endpoints работают; локального repository больше нет.

Первичный доступ в админку можно закрыть через Cloudflare Access для:


## LogJam

LogJam - отдельный сайт для приглашенных друзей и кураторов по адресу
`logjam.shmol.cc`. Он живет в этом же GitHub-репозитории, но собирается и
развертывается отдельным Cloudflare Worker. Публичный frontend портфолио при этом не
меняется.

Каталог LogJam показывает каждый опубликованный альбом ровно один раз, без Sets и
Selected Films. Внутри альбома фотографии идут одной вертикальной лентой; после конца
автоматически подгружается следующий альбом, а обычная кнопка Back возвращает в каталог.
Карточка каталога не показывает описание и теги: в первой строке стоят название и число
кадров, во второй - `kept`, `passed` и отметка `Sorted`. Полностью отсортированная карточка
не открывается, а в непрерывной ленте такой альбом пропускается целиком вместе с заголовком.
Интерфейс использует только белую и черную темы: первый визит следует системной теме,
а одна кнопка возле `LogJam` переключает и запоминает противоположную. После успешного
`keep/pass` кадр плавно уходит из ленты, следующие кадры поднимаются, а уже принятое
решение остается доступно только в соответствующей вкладке `My edit`. В ленте
`ArrowLeft` отклоняет кадр, `ArrowRight` сохраняет, а `Z` или `Cmd-Z` отменяет последнее
действие. Undo проходит через защищенный user-scoped private API; удаление решения и
согласование связанных активных подборок выполняются одной атомарной операцией.

Смотреть каталог можно без входа. Первая попытка выбрать или отклонить фотографию
переводит пользователя в Cloudflare Access для подтверждения email одноразовым кодом.
После проверки Worker на каждом приватном запросе сверяет нормализованный email с
`logjam_invites` в D1. Владелец добавляет и отзывает доступ в `/admin/logjam`; отзыв
действует со следующего запроса, но не удаляет работу куратора. Первая версия не
отправляет письмо-приглашение: владелец передает ссылку вручную. Выбор `keep/pass`
принадлежит паре `пользователь + фотография` и не зависит от исходного альбома.

Пользователь видит только свои решения и подборки. Новая подборка может смешивать
фотографии из любых исходных альбомов. Рабочая подборка редактируема, а Submit создает
ее неизменяемую версию для владельца. После дальнейшего редактирования можно отправить
следующую версию. Владелец просматривает версии в `/admin/logjam` и одной операцией
превращает выбранную версию в обычный draft Album, переиспользуя существующие Photo и
Asset без копирования R2-файлов. Когда этот album хотя бы один раз опубликован,
исходная пользовательская подборка блокируется навсегда.

LogJam использует ту же D1 `yakov_archive`, но пишет только в таблицы `logjam_*` до
момента явного owner promotion. Защитные пределы первой версии: не больше 20
подборок и 50 отправленных версий на пользователя, 500 фотографий в подборке,
20 версий одной подборки, 120 решений и 60 остальных приватных изменений в минуту.

Production-ресурсы LogJam, Access policy, домен и миграция создаются только после
отдельного подтверждения владельца. До этого реализация и данные проверки остаются
локальными.

## Где жить админке

Админку держим в этом же репозитории и в том же Next.js Worker:

```txt
/admin
  frontend админки
  защита Cloudflare Access
  API через Route Handlers / Worker bindings
```

Так проще быстрее собрать рабочую систему. Если админка вырастет в отдельный большой продукт, ее можно будет вынести в отдельное приложение позже.

## Публичные данные и API

Публичный frontend читает published-only данные прямо из D1. Он не зависит от
админских моков, portfolio manifest или browser `localStorage`.

Текущий поток:

```txt
страницы и интерфейс
  -> server components читают D1
  -> возвращают только published/not hidden
  -> изображения грузятся из R2 public assets
```

Изменения публикации появляются без пересборки сайта. Главная берет альбомы из
опубликованных Sets; `/albums` показывает все опубликованные альбомы.

## Seed Content

Фейковый/demo-контент можно оставить в проекте как рабочие fixtures для проверки дизайна, фильтров, сетов, альбомов и upload-flow.

Практическое правило:

- demo-альбомы должны быть явно отличимы в админке;
- их должно быть легко скрыть, удалить или сбросить;
- реальные альбомы добавляются рядом, без необходимости предварительно вычищать весь seed;
- перед production-публикацией важно проверить, какие demo-записи реально опубликованы.

На первых этапах нормально делать публичный и админский UI на фейковых альбомах. Пользователь удалит или скроет их позже через саму админку.

Отдельно от fixtures есть реальный стартовый импорт: 9 альбомов и 312 фотографий из принятого frontend. Эти записи должны стать настоящими `isDemo: false` данными в D1, а их JPEG должны загружаться напрямую в R2 и никогда не попадать в GitHub.

## Рабочая админка

Текущий MVP позволяет:

- создавать сеты;
- создавать альбомы;
- загружать JPEG-фотографии в альбом;
- сохранять порядок загрузки;
- назначать теги альбомам и фотографиям;
- скрывать и публиковать фото;
- отправлять альбомы и фото в корзину;
- восстанавливать из корзины;
- выбирать обложки;
- менять активные глобальные defaults.

Админка живет в этом же репозитории под `/admin`, закрыта Cloudflare Access для
`Jacobjshmol@gmail.com` и использует D1/R2 как единственный runtime source of truth.
